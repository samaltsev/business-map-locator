# NBH Business Locator — регламент разработки с оркестрацией Codex

**Версия документа:** 1.0  
**Дата:** 23 июля 2026  
**Проект:** NBH Business Locator  
**Исходная сборка:** Business Map Locator `1.3.2-beta29`  
**Основной продуктовый документ:** `docs/specification/NBH-Business-Locator-Master-Spec-v3.0.md`

---

## 1. Назначение документа

Этот документ определяет рабочий процесс разработки NBH Business Locator с использованием Codex в VS Code и внешней оркестрацией.

Роли разделены следующим образом:

- **Владелец продукта** определяет продуктовые приоритеты, проверяет интерфейс и принимает итоговый результат.
- **Оркестратор** анализирует ТЗ, текущее состояние кода и ответы Codex; готовит узкие промпты; оценивает изменения; определяет следующий шаг.
- **Codex** исследует локальный репозиторий, вносит согласованные изменения, запускает проверки и предоставляет доказательства результата.

Главный принцип:

> Ответ Codex не считается готовым результатом. Он является кандидатом на инженерное ревью и основанием для следующего шага.

---

## 2. Цель процесса

Ускорить разработку, не превращая скорость в накопление регрессий и архитектурного долга.

Процесс должен обеспечивать:

1. одну понятную цель на один цикл;
2. диагностику до изменения сложной логики;
3. минимально достаточные патчи;
4. сохранение обратной совместимости;
5. обязательные тесты и доказательства;
6. контролируемый переход от legacy-слоя к canonical architecture;
7. воспроизводимую сборку релизного ZIP;
8. соответствие Master Spec и Definition of Done.

---

## 3. Основные принципы

### 3.1. Один раунд — одна инженерная цель

Каждый промпт решает одну проблему или один тесно связанный набор причин.

Недопустимо объединять в один раунд:

- редизайн нескольких экранов;
- изменение REST-контракта;
- миграцию данных;
- оптимизацию карты;
- сборку релиза.

Исключение возможно только тогда, когда изменения являются неделимыми частями одной подтверждённой причины.

### 3.2. Диагностика предшествует патчу

Для ошибок с неясной причиной сначала выполняется отдельный диагностический раунд.

Codex должен:

1. воспроизвести или проследить симптом;
2. построить фактический runtime path;
3. определить canonical и legacy owners;
4. доказать причину ссылками на файлы, классы и функции;
5. предложить минимальный план исправления;
6. не менять код без прямого разрешения.

### 3.3. Фактический код важнее предположений

ROADMAP.md и Master Spec задают целевое состояние, но не доказывают текущее состояние реализации.

Перед изменением Codex проверяет:

- какой bootstrap реально выполняется;
- какие классы регистрируются;
- какие assets реально enqueue-ятся;
- какой REST endpoint вызывается;
- какие options/meta keys используются;
- нет ли параллельной legacy-реализации;
- какие тесты отражают поведение, а какие проверяют только структуру файлов.

### 3.4. Минимально достаточный патч

Патч должен устранять первопричину, а не маскировать симптом.

Приоритет действий:

1. исправить причину;
2. удалить или изолировать конфликтующую логику;
3. добавить regression test;
4. обновить документацию;
5. выполнить проверки;
6. только при необходимости проводить расширенный рефакторинг.

### 3.5. Явные границы изменений

Каждый implementation prompt содержит:

- разрешённые области;
- запрещённые области;
- публичные контракты, которые нужно сохранить;
- допустимость или запрет миграций;
- допустимость или запрет изменения UI;
- требования к legacy aliases;
- критерии приёмки.

### 3.6. Никаких неподтверждённых заявлений

Фраза «всё проверено» допустима только при перечислении реально выполненных проверок и их результатов.

Если WordPress runtime или браузер не были доступны, Codex обязан прямо это указать.

### 3.7. Исправление поставляется с защитой от регрессии

Для каждого существенного исправления необходимо:

- расширить существующий тест или добавить новый;
- описать, почему тест падал бы до исправления;
- проверить поведение, а не только наличие строки, файла или CSS-селектора;
- по возможности добавить integration/JS/E2E coverage для критического контура.

### 3.8. Данные проходят полный пользовательский контур

Функция считается реализованной только при завершённом пути:

> Admin input → validation → storage → index → REST → frontend → tests → documentation.

Наличие поля в UI, meta key или DTO отдельно не означает готовность функции.

## 4. Метод «пинг-понг»

### Шаг 1. Подготовка промпта

Оркестратор:

- сопоставляет задачу с Master Spec;
- анализирует доступный код и предыдущий ответ;
- определяет один тип раунда;
- формулирует ограничения и критерии приёмки;
- требует доказательства и формат отчёта.

### Шаг 2. Выполнение в Codex

Владелец проекта отправляет промпт в Codex в корне репозитория.

Codex:

- исследует код;
- выполняет только разрешённые действия;
- запускает проверки;
- возвращает структурированный отчёт и diff summary.

### Шаг 3. Передача результата

Для ревью передаются:

- полный ответ Codex;
- `git diff --stat`;
- `git diff` или commit hash;
- результаты тестов и lint;
- логи/скриншоты/Network data для runtime/UI-задач;
- собранный ZIP только на release-этапе.

### Шаг 4. Ревью оркестратора

Оркестратор проверяет:

- доказана ли причина;
- соответствует ли патч задаче;
- не расширена ли область изменений;
- не нарушены ли публичные контракты;
- нет ли нового дублирования legacy/new;
- достаточны ли тесты;
- выполнены ли реальные проверки;
- соответствует ли результат Master Spec.

### Шаг 5. Следующий промпт

Следующий раунд выбирается по результату:

- дополнительная диагностика;
- реализация подтверждённого плана;
- исправление замечаний ревью;
- regression hardening;
- runtime/UI verification;
- release preparation.

---

## 5. Типы Codex-раундов

### A. Diagnostic

Цель: установить факты и первопричину.  
Изменение кода: запрещено.  
Результат: runtime map, findings, risks, proposed patch plan.

### B. Implementation

Цель: реализовать ранее подтверждённое изменение.  
Изменение кода: разрешено в заданных границах.  
Результат: патч, тесты, проверки, manual verification steps.

### C. Review

Цель: проверить существующий diff или commit.  
Изменение кода: обычно запрещено.  
Результат: замечания по severity, regressions, missing tests, recommendation.

### D. Hardening

Цель: усилить тесты, edge cases, безопасность, accessibility или performance после рабочего патча.  
Изменение кода: ограничено защитными изменениями.

### E. Release

Цель: синхронизировать версии, changelog, документацию и собрать чистый ZIP.  
Разрешается только после принятия implementation и verification раундов.

## 6. Стандарт промпта

Каждый промпт содержит следующие разделы:

```text
РОЛЬ
РЕЖИМ РАУНДА
КОНТЕКСТ ПРОЕКТА
ТЕКУЩАЯ ЦЕЛЬ
НАБЛЮДАЕМЫЙ СИМПТОМ
ОЖИДАЕМОЕ ПОВЕДЕНИЕ
ИСТОЧНИКИ ИСТИНЫ
НАЧАЛЬНЫЕ ФАЙЛЫ ДЛЯ АНАЛИЗА
ОБЯЗАТЕЛЬНЫЙ ПОРЯДОК РАБОТЫ
ОГРАНИЧЕНИЯ
КРИТЕРИИ ПРИЁМКИ
ОБЯЗАТЕЛЬНЫЕ ПРОВЕРКИ
ФОРМАТ ОТВЕТА
STOP CONDITIONS
```

### Stop conditions

Codex обязан остановиться и не менять код, если:

- причина не доказана;
- требуемое изменение ломает явно защищённый контракт;
- обнаружено расхождение между задачей и Master Spec;
- нужен destructive migration без утверждённого плана;
- рабочее дерево уже содержит несвязанные изменения, которые мешают безопасному diff;
- отсутствуют необходимые файлы или окружение.

Вместо импровизации Codex возвращает блокер и рекомендуемый следующий шаг.

## 7. Уровни проверки

### Уровень A — статический

- PHP syntax lint;
- JavaScript syntax check;
- PHPCS;
- PHPStan;
- поиск deprecated/unsafe patterns по задаче.

### Уровень B — automated tests

- PHPUnit;
- targeted regression tests;
- schema/migration tests;
- JS tests, когда инфраструктура доступна.

### Уровень C — WordPress runtime

- activation/upgrade;
- admin screen load;
- save action;
- REST request;
- index sync;
- provider initialization.

### Уровень D — browser/manual

- Console;
- Network;
- desktop/mobile;
- keyboard;
- loading/error/empty states;
- provider failure;
- multiple instances;
- visual regression.

В отчёте каждый уровень получает статус:

- `PASS`;
- `FAIL`;
- `NOT RUN` с причиной.

## 8. Оценка результата Codex

| Критерий | Вес |
|---|---:|
| Первопричина доказана | 20% |
| Решена заявленная задача | 20% |
| Область изменений минимальна | 10% |
| Сохранена совместимость | 10% |
| Добавлена защита от регрессии | 10% |
| Соблюдена архитектура | 10% |
| Проверки реально выполнены | 10% |
| Отчёт воспроизводим | 5% |
| Учтены security/accessibility/data safety | 5% |

Результат ниже **8/10** не принимается в release branch без дополнительного раунда.

Критические основания для отклонения независимо от оценки:

- destructive data loss;
- изменение REST/meta/options без миграции и совместимости;
- скрытое отключение тестов;
- удаление функциональности вне scope;
- фиктивные результаты тестов;
- сборка ZIP из грязного дерева;
- добавление CDN или секретов;
- исправление UI путём глобального не изолированного CSS.

## 9. Git и контроль изменений

Рекомендуемый порядок:

1. создать baseline tag/commit для исходной beta29;
2. одна задача — одна ветка;
3. перед Codex проверить `git status --short`;
4. не смешивать пользовательские изменения с Codex-патчем;
5. после каждого принятого раунда делать отдельный commit;
6. version bump выполнять только в release-раунде;
7. хранить диагностические отчёты в `docs/audits/` при их долгосрочной ценности.

Рекомендуемое именование веток:

```text
codex/diag-settings-runtime
codex/fix-location-contract
codex/test-location-save-regression
release/1.3.2-beta30
```

Рекомендуемое именование commits:

```text
Audit settings runtime ownership
Fix destructive location meta save
Add location contract regression coverage
Prepare 1.3.2-beta30 release
```

## 10. Правила работы с legacy

До завершения архитектурного перехода Codex обязан для каждой затронутой функции определить:

- canonical owner;
- legacy owner;
- bootstrap registration;
- публичный контракт;
- допустимый migration/deprecation path.

Запрещено:

- создавать третью реализацию;
- оставлять два активных обработчика одной операции;
- удалять legacy alias без миграционного окна;
- переносить код без теста поведения;
- считать namespaced-класс canonical только из-за его расположения в `src/`.

## 11. Правила UI/CSS/JS

### UI

Сначала корректность данных и состояний, затем визуальная полировка.

Порядок:

1. data contract;
2. loading/error/empty states;
3. performance;
4. accessibility;
5. responsive behavior;
6. styling.

### CSS

Перед добавлением нового правила проверить:

- дублирующиеся selectors;
- page-specific scope;
- глобальные WordPress selectors;
- `!important`;
- старые неиспользуемые rules;
- конфликты shared/admin/page CSS.

### JavaScript

Для каждого workspace проверить:

- единственную инициализацию;
- scoped instance state;
- cleanup/destroy;
- AbortController;
- stale responses;
- duplicate listeners;
- provider assets loaded once;
- отсутствие глобальных конфликтующих selectors.

---

## 12. Правила performance-задач

Оптимизация принимается только при наличии измерений до и после.

Минимальные показатели:

- количество запросов;
- REST response size;
- число загруженных locations;
- время response/render;
- количество markers/cards;
- число повторных initialization calls;
- memory/DOM growth при возможности;
- наличие abort/debounce/cache.

Запрещено считать улучшением субъективное «стало быстрее» без измеримого сценария.

---

## 13. Release-процесс

Version bump и ZIP выполняются только после принятия кода.

Перед сборкой:

1. чистое рабочее дерево;
2. версии синхронизированы;
3. changelog обновлён;
4. tests/lint пройдены;
5. debug code отсутствует;
6. документация соответствует функциональности.

ZIP не должен содержать:

- `.git`;
- IDE settings;
- logs;
- temporary files;
- screenshots;
- nested ZIP;
- secrets/API keys;
- local absolute paths;
- dev-only dependencies, не предусмотренные release package.

После сборки:

1. распаковать ZIP в новую директорию;
2. проверить root folder;
3. повторить syntax lint;
4. проверить version parity;
5. вычислить SHA-256;
6. приложить release evidence.

## 14. Приоритет первого цикла

Первый цикл — **диагностический аудит beta29**.

Фокус:

- фактический bootstrap и ownership Settings Studio;
- enqueue новых и legacy assets;
- единственная или двойная инициализация карты;
- путь загрузки опубликованных точек;
- пагинация и состояние `0 / 807`;
- race conditions и stale responses;
- provider switching;
- фактический REST/search path;
- соответствие тестов реальному поведению.

В первом цикле запрещено изменять код.

---

## 15. Definition of Done для одного раунда

Раунд завершён только если:

- цель выполнена;
- выводы подтверждены evidence;
- ограничения соблюдены;
- изменения минимальны;
- tests добавлены или обоснованно не требуются;
- проверки перечислены с результатами;
- риски и ограничения раскрыты;
- следующий шаг однозначен;
- результат прошёл ревью оркестратора.

## 16. Практический режим моделей Codex

Рекомендуемый режим при внешней оркестрации:

- быстрые локальные поиски и простые механические изменения — быстрая модель/низкое reasoning;
- обычные узкие implementation-задачи — основная Codex-модель со средним reasoning;
- архитектурная диагностика, миграции, concurrency, REST/data contracts и code review — наиболее сильная доступная модель с высоким reasoning;
- `xhigh` использовать только для действительно сложных неоднозначных задач, поскольку узкий качественный промпт обычно важнее постоянного максимального compute.

Окончательный выбор делается по списку моделей, фактически доступных в установленной версии Codex и текущем тарифе.
